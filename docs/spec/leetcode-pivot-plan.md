# LeetCode 전환 수정 계획서 (구현 제외)

## 1. 배경

- BOJ 서비스 종료 공지(2026-04-28 종료 예정)에 따라 기존 BOJ 중심 흐름은 운영 리스크가 큼.
- 현재 확장프로그램의 핵심 가치(문제 이해 보조, 번역 지원, 학습 연속성)는 LeetCode 환경에서도 유효함.
- 따라서 단기적으로 서비스 연속성을 확보하기 위해 LeetCode 중심으로 제품 방향을 전환함.

## 2. 목표

- 사용자가 LeetCode 문제 페이지에서 즉시 번역된 문제 설명을 확인할 수 있게 함.
- 이미 번역된 문제는 DB/캐시에서 재사용하여 응답 속도와 비용을 최적화함.
- 원문 변경 시 번역본 무결성을 유지할 수 있는 관리 기준(버전/해시)을 도입함.

## 3. 범위 (In Scope)

- 문제 페이지 URL/슬러그 인식 체계 재정의 (BOJ -> LeetCode).
- 번역 조회 우선순위 정책 수립 (메모리 캐시 -> 로컬 DB -> 서버 DB -> AI 번역).
- 문제 단위 번역 저장 키 설계 (platform + slug + source_hash).
- 번역 품질 운영 정책 수립 (용어집, 검수 상태, 재번역 트리거).
- 사용자 UX 정책 수립 (원문/번역 토글, 번역 상태 표시, 신고/피드백).

## 4. 비범위 (Out of Scope)

- 실제 코드 구현 및 배포.
- LeetCode 컨텐츠 대량 수집 파이프라인 구축.
- 신규 결제 정책 또는 요금제 개편.

## 5. 핵심 정책

### 5.1 문제 식별 정책

- 지원 도메인: `leetcode.com`, `leetcode.cn` 우선.
- URL 패턴: `/problems/{slug}` 기준으로 문제를 식별.
- 문제 식별자: `platform`, `slug`, `source_hash` 조합을 기본 키로 사용.

### 5.2 번역 조회/저장 정책

- 조회 순서:
  1. 세션 메모리 캐시
  2. 로컬 저장소(IndexedDB 등)
  3. 서버 번역 저장소
  4. AI 번역 생성
- 저장 원칙:
  - 번역 결과는 원문 해시와 함께 저장.
  - 동일 슬러그라도 해시가 다르면 신규 버전으로 간주.

### 5.3 텍스트 처리 정책

- 번역 대상: 문제 설명 텍스트 본문.
- 보존 대상: 코드 블록, 수식, 입출력 포맷, 고유 식별자.
- UI 원칙: 사용자가 언제든 원문으로 복귀 가능해야 함.

### 5.4 운영/품질 정책

- 공통 용어집(알고리즘/자료구조 핵심 용어) 관리.
- 번역 상태 값 정의: `auto`, `reviewed`, `deprecated`.
- 원문 변경 감지 시 `deprecated` 처리 후 재번역 대기 상태 부여.

## 6. 단계별 수정 계획

### Phase 1. 전환 기반 정리

- BOJ 의존 지점 식별 및 LeetCode 대응 매핑 표 작성.
- URL 라우팅/도메인 화이트리스트 정책 확정.
- 데이터 모델 변경안(키, 버전, 상태값) 문서화.

### Phase 2. 번역 파이프라인 정책 정리

- 조회 우선순위 규칙 확정.
- 캐시 만료/갱신 기준 정의.
- 번역 실패/타임아웃 시 폴백 시나리오 정의.

### Phase 3. UX 및 운영 정책 정리

- 번역 상태 뱃지/토글 동작 시나리오 확정.
- 사용자 신고/피드백 반영 흐름 정의.
- 운영 지표 정의 (캐시 히트율, 번역 재사용률, 평균 응답시간).

### Phase 4. 리스크 점검 및 릴리즈 준비

- 이용약관/저작권 관련 준수 점검 항목 확정.
- 대량 요청 방지 정책(레이트 리밋, 온디맨드 처리) 확정.
- 롤백/비상 대응 정책 문서화.

## 7. 리스크 및 대응

- 정책/약관 리스크:
  - 대응: 대량 수집 금지, 사용자가 실제로 연 문제만 온디맨드 처리.
- 번역 정확도 리스크:
  - 대응: 용어집 + 신고 채널 + 재번역 루프 운영.
- 원문 변경 리스크:
  - 대응: 해시 기반 버전 분리와 자동 무효화 처리.
- 성능 리스크:
  - 대응: 다층 캐시 구조와 우선순위 조회 정책 적용.

## 8. 완료 기준 (Definition of Done)

- 전환 범위와 비범위가 문서로 합의됨.
- 데이터 키/버전/상태 정책이 확정됨.
- 조회 우선순위 및 폴백 규칙이 확정됨.
- 약관/운영 리스크 대응 체크리스트가 확정됨.
- 구현 착수 전 참조 가능한 단일 기준 문서로 승인됨.
